The Two Data Paths

Everything else in this app is a variation of these two flows:

🌐
Online path: User types → parser → addTransaction() server action → Prisma INSERT → revalidatePath() → UI updates
📴
Offline path: User types → parser → applyLocalMutation() → IndexedDB write + syncQueue entry → optimistic UI → [network returns] → drainQueue() → POST /api/sync → real ID replaces temp ID

Module 2
Next.js App Router

Next.js 15 uses the App Router — a file-system-based routing system where every folder inside app/ becomes a URL segment. Every component is a Server Component by default; you opt into client-side interactivity with "use client".

Directory Structure

File → URL mapping
app/
├── page.tsx                    → /  (redirects to /dashboard or /login)
├── layout.tsx                  → Root HTML shell
├── globals.css                 → Global Tailwind styles
├── (dashboard)/                → Route group (parentheses = no URL segment!)
│   ├── layout.tsx              → Shared layout: NavBar + main wrapper
│   ├── dashboard/
│   │   ├── page.tsx            → /dashboard
│   │   └── loading.tsx         → Streaming skeleton shown while fetching
│   └── transactions/
│       └── page.tsx            → /transactions
├── (auth)/
│   └── login/
│       └── page.tsx            → /login
└── api/
    ├── auth/[...nextauth]/
    │   └── route.ts            → /api/auth/* (NextAuth endpoints)
    └── sync/
        └── route.ts            → /api/sync  (offline sync)
💡
Route groups — folders in parentheses like (dashboard) group routes without adding to the URL. The path is /dashboard, not /(dashboard)/dashboard.

Server vs Client Components

Server ComponentClient Component
✅ Fetch data directly from DB✅ useState, useEffect
✅ Access server secrets / env vars✅ Event handlers (onClick, etc.)
✅ Zero JS bundle cost✅ Browser APIs (window, navigator)
❌ No useState / useEffect❌ Cannot access DB directly
❌ No event handlers❌ Adds to client JS bundle

In this app, the pattern is a server-to-client handoff:

app/(dashboard)/dashboard/page.tsx   ← Server Component
  ▪ Runs on the server
  ▪ Fetches data from DB (no round-trip from browser)
  ▪ Passes data as props
        │
        │ initialTransactions, initialTotalIncome, …
        ▼
components/DashboardContent.tsx      ← Client Component ("use client")
  ▪ Receives initial data once on mount
  ▪ Manages optimistic state updates
  ▪ Handles user interactions

The Dashboard Server Component

typescript — app/(dashboard)/dashboard/page.tsx 
// Server components can be async — no useEffect needed for data fetching
export default async function DashboardPage({ searchParams }: PageProps) {
  const { month, year } = getCurrentMonthYear();

  // Runs IN PARALLEL on the server (not sequentially)
  const [data, prevData, recurring] = await Promise.all([
    getDashboardData(month, year),
    getDashboardData(prevMonth, prevYear),  // for month-over-month diff
    getRecurringTransactions(),
  ]);

  // Pass to client component as props ("initial*" = server-fetched starting values)
  return (
    <DashboardContent
      initialTransactions={data.transactions}
      initialTotalIncome={data.totalIncome}
      initialTotalExpenses={data.totalExpenses}
      // … more props
    />
  );
}
📌
The initial* prefix is intentional — it signals these are starting values that the client component can diverge from as the user makes changes (optimistic updates).

URL-Driven Month Navigation

The URL ?month=3&year=2025 controls which data loads. The server component reads searchParams and passes the correct month/year to the database query. In Next.js 15, searchParams is a Promise and requires await.

Authentication with NextAuth

NextAuth v4 handles the entire authentication lifecycle from login to session management to route protection.

The Auth Flow

1
User submits login form

Email + password sent to POST /api/auth/signin/credentials

2
NextAuth credentials provider runs authorize()

Fetches user by email from DB, runs bcryptjs.compare(password, hash)

3
JWT session token created

Stored in an HTTP-only cookie — JavaScript in the browser cannot read it (XSS-safe)

4
Every subsequent request includes the cookie

Browser sends it automatically; middleware.ts validates it before allowing access

5
Server actions extract the user ID

getAuthenticatedUserId() reads the session and throws "Unauthorized" if missing

Route Protection — middleware.ts

typescript — middleware.ts 
export default withAuth(
  function middleware(req) {
    return NextResponse.next();  // Just proceed if authorized
  },
  {
    callbacks: {
      authorized: ({ token }) => !!token,  // Any valid JWT = OK
    },
    pages: { signIn: "/login" },
  }
);

export const config = {
  matcher: [
    // Negative lookahead: protect everything EXCEPT these paths
    "/((?!login|api/auth|_next/static|_next/image|favicon.ico|manifest.json|icons|sw.js).*)",
  ],
};
⚠️
The service worker file sw.js must be excluded from auth protection or it can't register in the browser. Same for manifest.json and icons — these are public PWA resources.

The Security Boundary in Server Actions

typescript — lib/actions.ts 
async function getAuthenticatedUserId(): Promise<string> {
  const session = await getServerSession(authOptions);
  if (!session?.user) throw new Error("Unauthorized");
  const userId = session.user.userId;
  if (!userId) throw new Error("Unauthorized");
  return userId;
}

// Every server action calls this FIRST before touching the database
export async function deleteTransaction(id: string) {
  const userId = await getAuthenticatedUserId();  // ← throws if no session

  // Ownership check — user A cannot delete user B's transactions
  const existing = await db.transaction.findFirst({ where: { id, userId } });
  if (!existing) throw new Error("Transaction not found");

  await db.transaction.delete({ where: { id } });
}

Module 4
Database Layer with Prisma

Prisma is an ORM (Object-Relational Mapper) — it translates between TypeScript objects and SQL. Instead of writing raw SQL you write typed TypeScript that Prisma converts into queries.

🔑
The killer feature: Prisma generates TypeScript types from your schema. The database shape and your code stay in sync automatically. A schema change breaks TypeScript compilation, not a runtime error.

The Schema

prisma — prisma/schema.prisma 
model Transaction {
  id        String   @id @default(cuid())  // CUID: shorter than UUID, URL-safe
  userId    String
  amount    Float                         // Always positive; direction = type field
  category  String
  note      String?                        // ? = optional (nullable)
  date      DateTime
  type      String                         // "income" or "expense"
  labels    String[] @default([])          // Array of strings (Postgres ARRAY)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  @@index([userId])
  @@index([userId, date])  // Composite index for fast date-range queries
}

model RecurringTransaction {
  id        String    @id @default(cuid())
  userId    String
  name      String
  frequency String    // "daily" | "weekly" | "monthly" | "yearly"
  startDate DateTime
  endDate   DateTime?
  lastRun   DateTime?  // null = never posted
  isActive  Boolean   @default(true)
  // …other fields
}

Common Query Patterns

typescript — lib/actions.ts 
// Read — all transactions in a date range
const transactions = await db.transaction.findMany({
  where: {
    userId,
    date: { gte: start, lte: end },  // gte = >=, lte = <=
  },
  orderBy: { date: "desc" },
});

// Aggregate — total amount
const total = await db.transaction.aggregate({
  where: { userId, type: "expense", date: { gte: start, lte: end } },
  _sum: { amount: true },  // SQL: SUM(amount)
});

// Atomic batch — both succeed or both fail
await db.$transaction([
  db.transaction.create({ data: { /* new transaction */ } }),
  db.recurringTransaction.update({
    where: { id },
    data: { lastRun: new Date() },
  }),
]);

The Singleton Pattern

Next.js restarts the module system on every file change in development. Without this pattern, each hot-reload would open a new database connection, quickly exhausting the connection pool.

Module 5
Server Actions (The Mutation Layer)

Server Actions are functions marked with "use server" that run on the server but can be called from client components as if they were regular functions. No REST API boilerplate needed.

How They Work

typescript — lib/actions.ts (server) 
"use server";  // ← entire file runs on the server

export async function addTransaction(data: { category: string; amount: number }) {
  const userId = await getAuthenticatedUserId();  // always verify first
  const tx = await db.transaction.create({ data: { userId, ...data } });
  revalidatePath("/dashboard");   // bust the Next.js render cache
  revalidatePath("/transactions");
  return tx;  // return value comes back to the client
}
typescript — components/ExpenseInput.tsx (client) 
"use client";
import { addTransaction } from "@/lib/actions";  // import like any function

async function handleSubmit() {
  // Called like a regular async function — Next.js serializes it as POST
  const result = await addTransaction({ category: "Food", amount: 20 });
  console.log(result.id);  // real CUID from the database
}
⚡
Under the hood, Next.js converts server action calls into POST requests with arguments serialized. You get type-safety across the network boundary — TypeScript will catch mismatched argument types at compile time.

Cache Invalidation

After a mutation, revalidatePath tells Next.js to re-fetch and re-render those pages on the next request. The root / is intentionally not revalidated:

⚠️
Do not call revalidatePath("/") — the root page is just a redirect. Revalidating it triggers a navigation loop. Only revalidate /dashboard and /transactions.

Module 7
State Management & Optimistic UI

State is managed with plain React hooks inside DashboardContent.tsx. No Redux — for an app of this size that would be premature overhead.

What is Optimistic UI?

Update the UI immediately before the server confirms the change. If the server succeeds, swap the temporary data for real data. If it fails, roll back. This makes the app feel instant.

Optimistic Update Flow
User clicks "Add" for "Food RM 20"
        ↓
Generate tempId = "temp_1746000000_abc"
        ↓
Add { id: tempId, category: "Food", amount: 20 } to local state
        → UI shows transaction IMMEDIATELY (no spinner, no wait)
        ↓
Call addTransaction() server action in background
        ↓
Server returns { id: "cm4realid..." }   ← real CUID from DB
        ↓
handleReplace(tempId, "cm4realid...")   ← swap in state
        ↓
Both IDB and React state now have the real ID

The State Slice

typescript — components/DashboardContent.tsx (simplified) 
// All initialized from server-fetched initial* props
const [transactions,    setTransactions]    = useState(initialTransactions);
const [pendingItems,    setPendingItems]    = useState([]);    // from IDB
const [totalIncome,     setTotalIncome]     = useState(initialTotalIncome);
const [totalExpenses,   setTotalExpenses]   = useState(initialTotalExpenses);
const [categoryData,    setCategoryData]    = useState(initialCategoryData);

async function handleAdd(parsed) {
  const tempId = `temp_${Date.now()}`;

  // 1. Optimistic update
  setTransactions(prev => [{ id: tempId, ...parsed }, ...prev]);
  setTotalExpenses(prev => prev + parsed.amount);

  try {
    // 2. Server call (async)
    const result = await addTransaction(parsed);
    handleReplace(tempId, result.id);  // 3. Swap temp → real
  } catch {
    // 4. Roll back on failure
    setTransactions(prev => prev.filter(t => t.id !== tempId));
    setTotalExpenses(prev => prev - parsed.amount);
  }
}

Why Not startTransition?

⚠️
React 18 does not properly track async transitions in startTransition(async fn). State updates can fire in the wrong order. This app uses plain async/await with a useState loading flag instead.

Module 8
Offline-First Architecture

This is the most sophisticated part of the codebase. Five interlocking layers work together to make the app function without a network connection.

Layer 1 — IndexedDB (lib/idb.ts)

IndexedDB is a browser database — structured, persistent, works offline. The idb library wraps the raw callback-based API with Promises.

IndexedDB Structure
Database: "expense-tracker-v1"
│
├── Object Store: "transactions"
│   Key: id (string)
│   Indexes: userId, date, syncStatus
│   Extra fields: syncStatus, syncError (beyond DB schema)
│
│   syncStatus values:
│   ├── "synced"          ← server has the latest version
│   ├── "pending"         ← created offline, never sent
│   ├── "pending-update"  ← exists on server, update queued
│   └── "pending-delete"  ← exists on server, delete queued
│
└── Object Store: "syncQueue"
    Key: queueId (autoIncrement integer)
    Fields: op, tempId, payload, createdAt
    Purpose: ordered list of mutations to replay on reconnect

Layer 2 — Sync Logic (lib/sync.ts)

typescript — lib/sync.ts (simplified) 
// applyLocalMutation — the offline WRITE path
async function applyLocalMutation(op: "add" | "update" | "delete", data) {
  if (op === "add") {
    const tempId = `pending_${Date.now()}_${random()}`;
    await putTransaction({ ...data, id: tempId, syncStatus: "pending" });
    await enqueueOp({ op: "add", tempId, payload: data });
    return tempId;
  }

  if (op === "update") {
    const existing = await getTransaction(data.id);
    if (existing.syncStatus === "pending") {
      // Never synced — update in place, modify queue entry (no double-queue)
      await patchTransaction(data.id, data);
      await updateQueuePayload(data.id, data);
    } else {
      // Synced — mark for update, enqueue new op
      await patchTransaction(data.id, { ...data, syncStatus: "pending-update" });
      await enqueueOp({ op: "update", id: data.id, payload: data });
    }
  }
}

A regular REST API route (not a server action) because service workers cannot call server actions — they're not in a React rendering context.

📌
This endpoint mirrors all the ownership checks from lib/actions.ts. The same userId verification happens here — no shortcuts just because it's called by the service worker.

Complete Offline Flow

End-to-end offline sequence
── OFFLINE ─────────────────────────────────────────────────────

User: "food 20"
  ↓ isOnline === false
ExpenseInput → applyLocalMutation("add", data)
  ├─ IDB transactions: { id: "pending_123", syncStatus: "pending" }
  └─ IDB syncQueue:    { queueId: 1, op: "add", tempId: "pending_123" }
  ↓
UI shows item with amber "Pending" badge

── RECONNECT ───────────────────────────────────────────────────

  ↓
SyncProvider → setTimeout(syncNow, 500)
  ↓
drainQueue()
  ├─ read syncQueue: [{ op: "add", tempId: "pending_123" }]
  ├─ POST /api/sync { op: "add", payload: { category: "Food", ... } }
  │       ↓ server: INSERT → { id: "cm4real..." }
  ├─ replaceTempId("pending_123", "cm4real...")  ← atomic IDB tx
  └─ deleteQueuedOp(1)
  ↓
router.refresh() → amber badge disappears

── TAB WAS CLOSED WHILE OFFLINE ────────────────────────────────

Browser gets network (no tab open)
  ↓ Service Worker fires "sync" event (tag: "expense-sync")
  ↓
drainQueueFromSW()
  ├─ opens IDB via raw cursor API (no React, no idb library)
  └─ POSTs each queued op to /api/sync

Natural Language Parsing

The parser in lib/parser.ts converts free-form text into structured transaction data. This reduces friction for the most common action in the app.

Input Examples

InputOutput
food 20category: Food, amount: 20, type: expense
salary 5000category: Salary, amount: 5000, type: income
grab rm15category: Grab, amount: 15, type: expense
coffee 4.5 starbucks #date #workcategory: Coffee, amount: 4.5, note: "starbucks", labels: ["date", "work"]

Parsing Algorithm

Token classification
Input: "coffee 4.5 starbucks #date #work"
        │      │   │          │     │
        │      │   │          └─────┘── Labels (# prefix → stripped, lowercased)
        │      │   └─────────────────── Note (after amount, not a label)
        │      └─────────────────────── Amount (numeric, strips rm/$)
        └────────────────────────────── Category (tokens before amount)

Steps:
  1. Tokenize by whitespace
  2. Extract #label tokens → remove from main list
  3. Find numeric token → strip currency prefix → parse float
  4. Tokens BEFORE number = category words (capitalize each)
  5. Tokens AFTER number (not labels) = note
  6. Check if any category word is in INCOME_KEYWORDS
     → "salary", "freelance", "dividend", "bonus", "gift", "refund", …
typescript — lib/parser.ts (simplified) 
const INCOME_KEYWORDS = new Set([
  "salary", "income", "freelance", "dividend", "interest",
  "bonus", "gift", "refund", "allowance", "commission",
  // …37 keywords total
]);

function stripCurrencyPrefix(token: string): string {
  return token.replace(/^(rm|\$|€|£|¥|₹|usd|aud)/i, "");
}

export function parseExpenseInput(input: string): ParsedExpense | null {
  const tokens = input.trim().split(/\s+/);

  // Extract labels
  const labels = tokens.filter(t => t.startsWith("#"))
                       .map(t => t.slice(1).toLowerCase());
  const rest = tokens.filter(t => !t.startsWith("#"));

  // Find amount
  const amountIdx = rest.findIndex(t => !isNaN(parseFloat(stripCurrencyPrefix(t))));
  if (amountIdx === -1) return null;

  const categoryWords = rest.slice(0, amountIdx);
  const category = categoryWords.map(capitalize).join(" ");
  const isIncome = categoryWords.some(w => INCOME_KEYWORDS.has(w.toLowerCase()));

  return { category, amount, type: isIncome ? "income" : "expense", labels };
}

Recurring Transactions

Recurring transactions are rules stored in the database. The user manually "posts" them when due (instead of auto-posting, which would require a cron job).

Status Logic

typescript — lib/utils.ts 
function getNextDueDate(frequency, startDate, lastRun): Date {
  const base = lastRun ?? startDate;  // null lastRun = never posted
  switch (frequency) {
    case "daily":   return addDays(base, 1);
    case "weekly":  return addDays(base, 7);
    case "monthly": return addMonths(base, 1);
    case "yearly":  return addYears(base, 1);
  }
}

function getRecurringStatus(nextDue, endDate): Status {
  if (endDate && today > endDate)              return "ended";
  if (today > nextDue)                         return "overdue";
  if (differenceInDays(nextDue, today) <= 3)   return "due";
  return "upcoming";
}

Atomic Posting

typescript — lib/actions.ts 
// db.$transaction = SQL transaction: both succeed or both fail
await db.$transaction([
  // 1. Create the actual transaction
  db.transaction.create({ data: { userId, category, amount, date: new Date() } }),

  // 2. Update lastRun so next due date advances
  db.recurringTransaction.update({
    where: { id },
    data: { lastRun: new Date() },
  }),
]);

Deterministic Category Colors

typescript — lib/utils.ts 
export function stringToColor(str: string): string {
  let hash = 0;
  for (let i = 0; i < str.length; i++) {
    hash = str.charCodeAt(i) + ((hash << 5) - hash);
  }
  const hue = Math.abs(hash) % 360;
  return `hsl(${hue}, 65%, 55%)`;  // fixed saturation/lightness
}
// "Food" always → same hue. No stored mapping needed.
// 65% saturation + 55% lightness = visible on dark background

export async function amountMasks(page: Page) {
  // All currency amounts use .tabular-nums — blur them so
  // daily spending changes don't break snapshots
  await page.addStyleTag({
    content: ".tabular-nums { filter: blur(4px); }",
  });

DecisionReason
Server Components for data fetchingZero client JS cost; data available at render time, no loading spinner
Client Component for interactivityuseState/useEffect only work in client components

IndexedDB for offline storageSurvives page reloads; structured queries; same data shape as server
Service Worker for background syncWorks even when the tab is closed
